# Teaching Patterns

> 讲懂不是“把论文换成中文”，而是让读者在脑子里建立可操作的结构。

---

## 1. 四层讲解

每个核心概念按四层写：

### 第一层：一句话直觉

先回答“它想解决什么问题”，不出现公式：

> 一句话：把 A 变成 B，但不用每次都重新算。

### 第二层：定义/公式，逐符号翻译

公式不是摆设，每个符号都要有中文解释：

| 符号 | 含义 | 代码/形状 |
|---|---|---|
| $x$ | 输入函数 | `[B,H,W]` |
| $W$ | 可学习变换 | `nn.Conv2d` |

然后给“读法”：

> 这个公式在说：先把输入拆成不同尺度，再在每个尺度上做一次可学习的加权组合。

### 第三层：最小例子 / 代码

- 数学/算法：手算一个 2×2 或 1D 的小例子。
- 代码：给输入/输出形状，逐行对照。
- 非代码领域：给一个真实案例，按步骤走一遍。

### 第四层：常见误解与边界

至少 3 条：

- 你以为 A，其实 B。
- 这个结论只在 C 条件下成立。
- 论文这样说，代码实际那样做。

---

## 2. 类比的使用

好的类比：

> 傅里叶像“食材清单”，知道有哪些频率，但不知道什么时候下锅；小波像“可移动的显微镜”，能看到某个位置有什么尺度。

必须跟一句边界：

> 这个比喻不准确的地方：小波不是真的“看”，它只是用局部基函数做内积。

不要用类比替代定义；类比只负责建立第一印象。

---

## 3. 公式讲法

顺序：

1. 这个公式解决什么问题？
2. 每个符号是什么？
3. 如果所有符号都取 1，公式变成什么？
4. 哪一项是主项，哪一项是修正？
5. 代码里对应哪一行？
6. 如果这一项写错，会发生什么？

不要：

- 只写“由公式可得”
- 不解释下标
- 不解释维度
- 不解释为什么是这个形式

## 4. 代码讲法

### 4.1 三对照

| 公式 | 代码 | 形状 |
|---|---|---|
| $v_0=P(a)$ | `fc0(x)` | `[B,H,W,3] → [B,H,W,C]` |
| $\mathcal W(v)$ | `dwt(x)` | `[B,C,H,W] → 系数` |

### 4.2 逐行表

| 代码 | 含义 | 输入/输出 |
|---|---|---|
| `x = self.fc0(inp)` | 提升到高维 | `[B,H,W,3] → [B,H,W,C]` |
| `x = x.permute(0,3,1,2)` | 通道前置 | `[B,C,H,W]` |

### 4.3 运行契约

每个代码文档至少给：

```bash
python demo.py --epochs 2
```

和预期输出：

```text
input shape = ...
output shape = ...
loss = ...
```

没有运行命令的代码讲解，不算讲完。

## 5. 常见误解

每个核心概念写 3–5 条：

```markdown
### 误解 1：X 就是 Y

不是。X 是……，Y 是……。区别在于……
```

常见类型：

- 把“方法名”当“机制”
- 把“论文写法”当“代码实际”
- 把“验证集”当“测试集”
- 把“参数多”当“效果好”
- 把“训练 loss 降”当“泛化好”
- 把“相关”当“因果”

## 6. 自测题

每篇 3–5 题，deep 模式总计 60–100 题。

题型搭配：

| 类型 | 例子 |
|---|---|
| 概念解释 | 用自己的话解释 X |
| 公式推导 | 写出 X 的梯度/展开 |
| 代码阅读 | 这行代码输出什么形状 |
| 实验设计 | 如果要验证 X，最小实验是什么 |
| 边界判断 | 这个结论在什么条件下不成立 |
| 排错 | loss 不降，先查什么 |

答案放在 `<details>` 里：

```markdown
<details>
<summary>答案</summary>

……

</details>
```

最后加一个 teach-back：

> 合上讲义，用 3 分钟把“X 为什么有效”讲给一个外行听。

---

## 7. 每篇的收尾

固定三件套：

1. **如果你只记一件事**：一句话。
2. **自测**：3–5 题。
3. **下一步**：链接到下一篇。

---

## 8. 语言风格

- 短句；一段一个意思。
- 术语第一次出现：中文（English）。
- 不写“显然”“众所周知”“不难发现”。
- 不堆“首先/其次/最后”；用标题组织。
- 不把“负结果”写成“失败”，写成“边界/反例/未解决”。
- 不把“推测”写成“事实”。

---

## 9. 非代码领域

把“代码层”替换成：

- 数学：手算例题、反例、图形
- 法律：案例、条文对照、争点
- 语言：例句、错误句、改写
- 历史：时间线、史料对照、争议
- 工程：系统图、故障案例、操作步骤

四层结构不变：直觉 → 定义 → worked example → 误区/边界。
